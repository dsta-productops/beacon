This tutorial follows one example project, SKYPROTECT, from raw interview notes to a prototype that real users can test. You do not need a background in product management or design.

By the end you will have:

- **Research documents** in Confluence, each traced to its sources (steps 3, 5, 6, 7)
- **A requirements document** (PRD) (step 8)
- **A working prototype** built with PRIZM (step 9)
- **A test plan** (step 10)
- **A baseline and test results** to compare against (steps 4, 11)

## 1. Check the prerequisites
::step{id="prerequisites" phase="Setup"}

Confirm you have the access you need before you start.

- A Confluence account with permission to create a space. Everything you produce is stored in a Confluence space.
- An AI assistant connected to Confluence, such as Claude with the Confluence connector turned on. Step 2 uses it to build the demo Knowledge Base.
- Access to [CLARA](/tools/clara). It connects to Confluence directly, so there is nothing to install.
- Access to [DASH](/tools/dash), at [diux-dash.com](https://diux-dash.com).
- [Claude Code](/tools/claude-code) installed. You first need it in step 9.

If you are unsure about access, see the *Availability by environment* table on each tool page.

:::watch{title="Read this first"}
- CLARA builds on what you give it, so an early mistake carries through every later step. Check each result before you move on.
- If a document lands in the wrong place or cites nothing, stop and check that the Knowledge Base from step 2 exists and your source links point to real pages with real content.
:::

## 2. Set up the SKYPROTECT Knowledge Base
::step{id="knowledge-base" phase="Setup" tool="AI assistant"}

SKYPROTECT is a made-up drone-defence programme. One setup file describes everything in its Confluence space, and your AI assistant builds the space from it.

1. In Confluence, create an empty space called **SKYPROTECT** with the space key `SKYPR`. Create it yourself, because the setup file tells the assistant not to.
2. Download :file[skyprotect-setup.md]{href="/skyprotect-setup.md"}.
3. Open your AI assistant, attach the file and paste this prompt:
   ```prompt
   Set up the SKYPROTECT demo Knowledge Base in Confluence by following the attached setup file exactly. The SKYPROTECT space (key SKYPR) already exists, so do not create it. If anything cannot be created, stop and tell me. Do not retry or improvise.
   ```
4. Wait for it to finish. It creates the pages one level at a time, so this takes a few minutes. It then reports how many pages it created and gives you a link to the top-level **Knowledge Base** page.
5. Open that link in Confluence.

::screenshot{hint="the finished SKYPROTECT page tree in Confluence, with the Knowledge Base expanded"}

:::check
Under **Knowledge Base** are two tracks, **Programme-wide** and **Operator-console**, holding 51 pages in all, including 24 interview and observation notes (S01 to S16, WT01 to WT04, and the Field Alpha and Bravo shift notes). Click a citation such as S08 in the research synthesis to open that note.
:::

**If the assistant stops part-way:**
- It stops on purpose when something goes wrong, usually a missing permission or a space with the wrong key.
- Fix the cause and run the same prompt again.

The setup also files a finished example of most documents you make in steps 3 to 10. Compare each with your own to see what good looks like. For a real programme, ask CLARA to create the folder structure instead. See [the CLARA provisioning steps](/tools/clara#provisioning).

## 3. Find what is already known
::step{id="prior-knowledge" phase="Research" tool="CLARA"}

Review past projects, earlier write-ups and other teams' Confluence pages first, so you do not start from zero.

1. Paste this prompt into CLARA:
   ```prompt
   Use CLARA's `prior-knowledge-summariser` for SKYPROTECT.
   ```
2. Answer its questions about your programme name, track (or Programme-wide) and topic. Choose a specific topic, such as "how operators hand over between shifts", not "user research".
3. Give it your sources as **URL links** to Confluence pages, one link per page. Do not upload Markdown files.
   ```
   https://<your-confluence-site>/wiki/spaces/<space-key>/pages/<page-id>
   ```
4. Check the list of sources before CLARA writes the summary. Remove any pages that do not belong.

::screenshot{hint="CLARA's list of sources, with the page links it has picked up"}

:::check
A summary of patterns, contradictions and related work, filed under `Knowledge Base / [track] / Prior-knowledge / [topic]`. Each finding names the Confluence page it came from.
:::

:::example
`Programme-wide / Prior-knowledge / Counter-drone-systems`
:::

**If the summary is thin or generic:**
- Add more source material, such as interview notes or past write-ups.
- Narrow the topic and run the prompt again. A finding with no source is a guess, not a fact.

**If CLARA cannot see your space:**
- Check that you can open the SKYPROTECT space yourself.
- If you can, ask your CLARA contact to check its connection.

## 4. Measure how things are today
::step{id="baseline" phase="Research" tool="DASH"}

A **baseline** measures how things work today, so you can show later that your design is better. Do it before any interviews or design work.

1. Sign in at [diux-dash.com](https://diux-dash.com) and open your programme's workspace.
2. Create a session, choose **Baseline Testing**, and name the system people use today. For SKYPROTECT, that is the three-vendor toolchain of separate radar, RF and camera systems.
3. Share the link or QR code with people who use that system.

::screenshot{hint="the Baseline Testing session in DASH, showing the share link and QR code"}

:::check
Responses appear in DASH as people answer. Keep this session open, because you compare against it in step 11.
:::

**If you cannot find your programme's workspace:**
- Each programme has one DASH workspace. Ask your DASH contact to add you.

DASH asks about **SUS** (System Usability Scale, a short score for how easy a system is to use), look and feel, user needs, system performance and **CSAT** (customer satisfaction). It also tracks **OKRs**, which are goals with numbers attached.

## 5. Interview your users
::step{id="interviews" phase="Research" tool="CLARA"}

Surveys give you numbers. Interviews tell you why. CLARA writes the guide and you run the conversations.

1. Paste this prompt into CLARA, then tell it the topic and what you want to learn. If you are not sure, ask it to choose from the open questions in your prior-knowledge summary.
   ```prompt
   Use CLARA's `interview-guide-generator` for SKYPROTECT.
   ```
2. Run 5 to 7 conversations with the people who will use the system.
3. After each one, paste your notes into Confluence using the **Field Notes** template, exactly as you took them. Do not tidy them, because polished notes add your own bias.

:::check
A field-ready interview guide with questions, things to listen for and follow-up prompts. Your raw notes are in the Field Notes pages in the Knowledge Base.
:::

**For the SKYPROTECT demo:** do step 1 only. The 24 interview, walk-through and field notes are already filed under `Field-notes` in both tracks.

## 6. Make sense of the notes
::step{id="synthesise" phase="Research" tool="CLARA"}

**Synthesis** pulls the patterns out of many notes. CLARA reads them all in one pass and separates what is new from what you already knew.

1. Paste this prompt into CLARA:
   ```prompt
   Use CLARA's `research-synthesiser` for SKYPROTECT.
   ```
2. Give it your learning goals and the gaps you found in step 3. It uses them to judge what counts as new.

:::check
One research-synthesis page with recurring patterns, friction points, standout statements and success criteria, citing your field notes. The Knowledge Base is updated.
:::

:::example
`Operator-console / Research-synthesis` (the programme-wide version is under `Programme-wide / Research-synthesis`)
:::

## 7. Profile your users
::step{id="personas-journeys" phase="Research" tool="CLARA"}

Turn the research into three documents. Paste each prompt into CLARA in turn.

1. Create a **persona**: a profile of a typical user, with what they want, what frustrates them and the evidence.
   ```prompt
   Use CLARA's `persona-generator` for SKYPROTECT.
   ```
2. Create a **user journey**: the steps a person goes through, the moments that matter most, and where you could improve things.
   ```prompt
   Use CLARA's `journey-map-drafter` for SKYPROTECT.
   ```
3. Create a **service blueprint**: the journey plus what your team does behind the scenes and the systems that support both.
   ```prompt
   Use CLARA's `service-blueprint-drafter` for SKYPROTECT.
   ```

::screenshot{hint="a finished persona page in Confluence, with its evidence citations"}

:::check
Three new pages in the Knowledge Base, each claim pointing back to a quote or note from your research.
:::

:::example
`Operator-console / Personas / Console-operator` and `Operator-console / Journeys / Engage-incoming-threat`. The space has no service blueprint, so yours is the first.
:::

## 8. Write the requirements
::step{id="prd" phase="Research" tool="CLARA"}

A **PRD** (product requirements document) is one page everyone agrees on: the problem, who it is for, what the product must do and how you will know it worked. It is the most important output of Research.

1. Paste this prompt into CLARA:
   ```prompt
   Use CLARA's `prd-generator` for SKYPROTECT.
   ```
2. Read the draft, then edit it by hand. It becomes the input for your prototype.

:::check
A PRD with a problem statement, user goals, scope, functional requirements (what the product must do) and user stories (short descriptions of what a user wants to do and why).
:::

:::example
`Operator-console / PRDs / Console-v1`
:::

## 9. Build a prototype
::step{id="prototype" phase="Design" tool="Claude Code + PRIZM"}

A prototype is a working draft people can click through. Claude Code reads your PRD and PRIZM's rules, so the result follows DSTA standards without extra styling work.

1. If you have not already, install Claude Code by following the steps on the [Claude Code page](/tools/claude-code). Open an empty project folder and start it there.
2. Open the [Prototype-from-PRD scaffolder](/prompts/prototype-from-prd) prompt and paste your PRD where it asks. The prompt tells Claude Code to read PRIZM's `PRIZM.md` and `llms.txt` first.
3. Choose a PRIZM zone: **Enterprise** for websites and back-office tools, or **C3** for command-and-control systems.
4. When Claude Code lists three to five user flows, pick one to build first. Do not skip this question, because it stops Claude Code generating hundreds of lines you do not need.
5. Open the prototype in your browser. To change something, describe the change in plain English.

::screenshot{hint="the running prototype in the browser, next to Claude Code"}

:::check
A running prototype of your chosen flow, built from PRIZM components and semantic colour tokens such as `bg-bg` and `text-fg`, not raw colours.
:::

**If Claude Code invents components PRIZM does not have:**
- Stop it and ask it to check `lib/components-registry.ts` in the PRIZM repository before it generates anything more.

## 10. Plan the test
::step{id="test-plan" phase="Test" tool="CLARA"}

A test plan says who you will test with and what you will ask them to do. CLARA reads your PRD and personas to draft one.

1. Paste this prompt into CLARA:
   ```prompt
   Use CLARA's `test-plan-generator` for SKYPROTECT.
   ```
2. Review the plan and adjust the number of participants to fit your team.

:::check
A test plan with objectives, research questions, personas to recruit, participant numbers, scenarios and the tasks each person will try.
:::

:::example
`Operator-console / Test-plans / Console-v1-usability-test`
:::

## 11. Test and compare
::step{id="test" phase="Test" tool="DASH"}

Test the prototype, then compare the results with your baseline from step 4.

1. In DASH, create a session and choose **Prototype Test**. It covers usability (SUS), look and feel, user needs and CSAT.
2. Share the link or QR code with your participants and run the sessions as set out in your test plan.
3. Compare the results with your baseline session.
4. Ask **DASH AI** for recommendations. It suggests usability improvements based on industry standards.

::screenshot{hint="the DASH comparison view, baseline against prototype results"}

:::check
Side-by-side scores for the old system and your prototype, plus a list of suggested improvements. This is your evidence that the new design is better, or your guide to what to fix next.
:::
