## In short

Two groups write code in the Pipeline, and both increasingly use Claude Code:

- **The design side (ProductOps)** decides what to build and how it should work. It writes **functional code**: reference code built from product requirements documents (PRDs), capability storyboards and virtual prototypes. It is usually driven by user experience (UX) work, and sometimes by a developer working on their own. Design owns it.
- **The engineering side (DevSecOps)** builds, secures and ships the software. It writes **NFR code**, the code for the non-functional requirements: hardening (making the product secure and robust), integration and reliability. It is usually driven by developers. Engineering owns it.

The Quality Model makes sure both kinds of code meet the same bar. Every proposed change goes through the same automated checks in the engineering side's (DevSecOps) pipeline. Three more layers catch what automated checks cannot.

It also makes the handover smoother. Functional code is built on shared foundations: the design system, agreed patterns, and typed contracts (shared definitions of how the two kinds of code connect). Engineers can then add NFR work alongside the design side's work, not after it.

This split follows the [tripartite product structure](/product-roles): design owns functional code, and engineering owns NFR code.

## The four layers

Each layer works at a different point in the lifecycle. If a problem gets past one layer, another is likely to catch it before the product goes live.

### Layer 1: Prevention

**When:** before the code is written.

Every piece of code starts from the same baseline: consistent style, aligned architecture patterns, and baseline security and accessibility hygiene. Fewer problems get created, so the later layers have less to catch. This is the cheapest layer, because a problem that never occurs costs nothing to fix.

It works through three things, described further down this page: a rules file for Claude Code, ready-made PRIZM components, and typed contracts.

### Layer 2: Outcome validation

**When:** during design, and continuously after.

Checks that the product will deliver the result it is meant to, before effort is spent building the wrong thing. It uses test plans, usability testing, the product scorecard, and checks against goals with measurable targets (OKRs). [DASH](/tools/dash) measures the result and gives early warning when something is off.

The design side owns this layer.

### Layer 3: Automated scan

**When:** when a change is proposed. This step is called a pull request: the point where new code is put forward for adding to the product.

A set of automated tools checks everything a machine can check. It applies the same checks to all code, whoever wrote it:

- **Quality checks and linters** flag code that breaks style rules or quality standards.
- **SCA** (software composition analysis) finds known security weaknesses in third-party libraries the code relies on.
- **SAST** (static application security testing) reads the source code and looks for security flaws.
- **Container scanning** checks the packaged application for risky settings.
- **DAST** (dynamic application security testing) tests the running application the way an attacker would.

What the tools find goes into Vulnerability Management, the engineering side's process for tracking and fixing security issues. The engineering side owns this layer.

### Layer 4: Integration verification

**When:** after the changes are merged, meaning combined into the main codebase.

Once the engineering side's work is added on top of the design side's, the combined result goes through the Layer 3 scan again. Each part may pass on its own and still cause problems when joined. This layer catches those problems. It does not redo the engineering work, because Layer 1 should already have shaped it.

### Who owns what

Both sides take part in Layers 1 and 4. The design side owns Layer 2. The engineering side owns Layer 3.

## Where Layer 1 does the heavy lifting

Most of the quality is built in at Layer 1. Layer 3 is the safety net, and Layer 1 keeps most code from ever needing it.

Three things carry most of the load:

- **A rules file for Claude Code.** Each project has a file called `CLAUDE.md`, which Claude Code reads at the start of every session. It names the exact approaches to use, such as the shared API wrapper (the project's shared code for talking to the backend), the existing state store (where the app keeps its data), `ErrorBoundary` (the component that catches errors) and PRIZM form components, so Claude does not have to guess.
- **PRIZM components.** [PRIZM](/tools/prizm) is DSTA's design system. Its ready-made components already meet DSTA's standards for accessibility, theming and appearance, so code that uses them meets those standards automatically. If PRIZM has a component for the job, use it before writing your own or dropping to raw HTML:
  - Layout: `Frame`, `Stack`
  - Forms: `Input`, `Select`, `Checkbox`, `Textarea`
  - Interactive: `Button`, `Tabs`, `Sheet`, `Command`
  - Content: `Card`, `Heading`, `Text`
- **Typed contracts.** Shared type definitions at the boundary between functional and NFR code: written-down definitions of exactly what data and settings pass between the two. Engineers can add NFR work on top of a design-built prototype without redefining the prop shapes (the settings each screen component accepts) or guessing what was intended.

## Why four layers, not one

A single scan catches problems in syntax and code patterns. It does not catch drift in architecture, failures that only appear when parts are joined, or repeat offences that a fixed set of rules never learns from. The four layers exist because these problems arise at different points in the lifecycle:

- **Layer 1** shapes the code before it exists.
- **Layer 2** checks that the thing is worth building.
- **Layer 3** catches known problems that a rule can detect, such as hardcoded secrets (passwords or keys written into the code), vulnerable dependencies (libraries with known flaws), injection patterns (inputs crafted to run unintended commands) and accessibility failures.
- **Layer 4** catches problems that only appear once the two kinds of code are joined.

Each layer is necessary, but none is sufficient on its own. Together, they let the design side's code go through the same engineering pipeline as everyone else's, with the same confidence.

## Starter `CLAUDE.md`

Below is a ready-to-use starter file. Drop it into a project as it is, or edit it as a template.

> **Before use:** the rules refer to a project's real approaches, such as its shared code for talking to the backend, its error handling, and how it keeps track of data on screen. In the starter these are placeholders. The project's tech lead must check them and approve the file before it is turned on. A rule that names the wrong approach misleads Claude Code, and brings back the integration risk this file is meant to prevent.

Rules use MUST and SHOULD wording (firm instructions) because directive language measurably improves how consistently Claude Code follows a rule. The file does not say which layer enforces each rule, because the four layers above already cover that. Claude Code reads every line of this file at the start of every session, so keep it short.
