Picture your first week on a new project. Your supervisor has given you a brief. There is no requirements document, no user research, and no clear idea who you are building for. It is tempting to start coding straight away.

Don't. This tutorial shows you the quicker route. You will follow one example project, SKYPROTECT, from raw interview notes to a prototype that real users can try. You do not need a background in product management or design.

By the end, you will have:

- A set of research documents in a GitLab wiki, each one traceable to its sources.
- A requirements document that says what to build and for whom.
- A working prototype built with PRIZM, DSTA's design system.
- A test plan, and a way to measure whether the new design beats what users have today.

## How the pieces fit

ProductOps decides *what* gets built. It sits beside DevOps, which secures and ships the software, and MLOps, which trains and deploys models. This tutorial covers ProductOps, which has three phases:

- **Research**: find out who the work is for and what problem you are solving.
- **Design**: turn that into a prototype.
- **Test**: check the prototype works for real people.

You will use four tools along the way:

| Tool | In plain terms | You use it to |
|---|---|---|
| [CLARA](/tools/clara) | An AI assistant that reads your wiki pages and writes documents back into them. | Do the research and write the requirements and test plan. |
| [DASH](/tools/dash) | A survey and scorecard tool. | Measure how things are today, then how your prototype compares. |
| [Claude Code](/tools/claude-code) | An AI assistant that writes code from plain-English instructions. | Build the prototype. |
| [PRIZM](/tools/prizm) | DSTA's design system: ready-made screen parts that follow DSTA standards. | Give the prototype a consistent look and behaviour. |

## Before you begin
::step{id="before-you-begin"}

Check that you have the following. Each tool page tells you which environments it runs in.

- **A GitLab project with its wiki enabled and initialised.** Everything you produce is stored in that wiki, so you need the Developer role or above on the project.
- **Git, with credentials already set up.** Wiki pages are files in a git repository. Your assistant writes them through git, using the credentials on your machine. Never paste a token into a chat.
- **An AI assistant that can run git.** Use the Claude Code plugin (extension) installed in your IDE, such as VS Code. Do not use the command-line version or the desktop app. Step 2 uses it to build the demo Knowledge Base for you. It needs no other GitLab connection. It works only through plain git commands.
- **Access to [CLARA](/tools/clara).** She reads your wiki and, when you give the go-ahead, files documents into it through git. You install her in step 1 by copying one file into your workspace.
- **Access to [DASH](/tools/dash).** Sign in at [diux-dash.com](https://diux-dash.com).
- **[Claude Code](/tools/claude-code) installed.** Install the Claude Code plugin in your IDE. It is also your setup assistant in step 2, and you need it again from step 9. New to git or IDEs? Follow the optional setup step below.

:::note{title="Not sure you have access?"}
Check the *Availability by environment* table on each tool page, or ask the contact listed there before you start.
:::

## Optional: set up git and your workspace
::step{id="workspace" phase="Setup" tool="Git + VS Code"}

Skip this step if you already use git, an IDE and Claude Code. If you have never used them, it takes about 20 minutes and you only do it once. You will end up with an empty folder, open in an IDE, with the Claude Code plugin installed. That is all the setup assistant in step 2 needs.

:::note{title="Which Claude Code?"}
Install the **Claude Code plugin** (extension) in your IDE and use its chat panel. Do not install the command-line version, and do not use the Claude desktop app, for this tutorial.
:::

1. **Install git.** Download it from [git-scm.com](https://git-scm.com/downloads) and accept the default options. Git is the tool that saves versions of your files and sends them to GitLab.
2. **Install an IDE.** An IDE is a text editor with a terminal built in. These steps use Visual Studio Code, from [code.visualstudio.com](https://code.visualstudio.com).
3. **Create an empty workspace folder.** Make a new folder on your computer, for example `skyprotect-workspace`. In VS Code, choose **File > Open Folder** and select it. The setup assistant will clone the wiki into this folder for you.
4. **Open the built-in terminal.** In VS Code, choose **Terminal > New Terminal** (or press :kbd[Ctrl] + :kbd[\`]). A panel opens at the bottom. Check git is installed by typing the line below and pressing :kbd[Enter]. You should see a version number.
   ```prompt
   git --version
   ```
5. **Tell git who you are.** Git stamps your name on every commit. Paste these two lines one at a time, replacing the name and email with your own:
   ```prompt
   git config --global user.name "Your Name"
   ```
   ```prompt
   git config --global user.email "you@example.com"
   ```
6. **Install the Claude Code plugin.** In VS Code, open the Extensions view (the square icon in the left bar, or :kbd[Ctrl] + :kbd[Shift] + :kbd[X]), search for **Claude Code**, and choose **Install**. Follow the IDE steps on the [Claude Code page](/tools/claude-code) if anything differs. Then open the Claude panel and sign in when asked.
7. **Create the GitLab project.** In GitLab, choose **New project > Create blank project**. Name it **SKYPROTECT**. Untick **Initialize repository with a README**. Leave the wiki enabled (it is on by default), then choose **Create project**.
8. **Initialise the wiki with a first page.** In the project, open **Plan > Wiki** and choose **Create your first page**. Set the title to `home`, type any placeholder text, and choose **Create page**. This is what creates the wiki's git repository. Do not add any other pages. The setup replaces this placeholder with the real home page.
9. **Copy the wiki clone URL.** On the wiki page, choose **Clone repository** and copy the HTTPS address. It ends in `.wiki.git`. You will paste it into the prompt in step 2.
10. **Sign in to GitLab from git.** The first time git talks to GitLab, a browser window or a prompt in the terminal asks you to sign in. Do it there. If it asks for a token, create a personal access token in GitLab with the `write_repository` scope and type it only into that prompt. Never paste a token into a chat or a file.

:::check
VS Code is open on your empty workspace folder. In its terminal, `git --version` prints a version number and the Claude panel opens and answers. In GitLab, the SKYPROTECT project exists, its wiki holds a single `home` page, and you have copied the wiki clone URL. Now go on to step 1, installing CLARA.
:::

:::watch{title="If git says it does not know who you are, or a command is not found"}
Close the terminal and open a new one, so it picks up the freshly installed tools. If `git` is still not found, run the git installer again. If git asks who you are, repeat the two `git config` lines.
:::

## 1. Install CLARA
::step{id="install-clara" phase="Setup" tool="CLARA"}

CLARA is a **skill**: a single Markdown file that tells Claude how to draft research documents and file them in your wiki. There are two ways to give it to Claude. Pick one. You need your workspace folder open in your IDE first (see the optional setup step above).

:::::tabs
::::tab{value="file" label="File method"}
Copy the skill file into a skills folder, once. After that CLARA is always available. This tutorial uses the project level, because it is easy to see in your IDE and affects nothing else on your machine.

| Level | Folder | CLARA is available |
|---|---|---|
| Project (used here) | `.claude/skills/clara-gitlab/` inside your workspace folder | Only when that folder is open |
| User | `~/.claude/skills/clara-gitlab/` in your home folder | In every project on your machine |

1. Download the skill file: :file[clara-gitlab.md]{href="/clara-gitlab.md"}. It usually lands in your Downloads folder.
2. **Create the folders in your IDE.** In the file list on the left (the Explorer), right-click an empty space and choose **New Folder**. Name it `.claude` (with the dot at the start). Right-click that folder, choose **New Folder**, and name it `skills`. Right-click `skills`, choose **New Folder**, and name it `clara-gitlab`. You now have `.claude > skills > clara-gitlab`.
3. **Add the file.** Open your Downloads folder in **Finder** (Mac) or **File Explorer** (Windows). Drag `clara-gitlab.md` into the `clara-gitlab` folder in your IDE's file list and drop it there. If your IDE asks to confirm the move, confirm.
4. **Rename it to `SKILL.md`.** In the IDE's file list, right-click `clara-gitlab.md`, choose **Rename**, type `SKILL.md` in capitals, and press :kbd[Enter].
5. Start a new chat in the Claude panel so it picks up the skill. If it still does not appear, reload the IDE window (**Developer: Reload Window** in the command palette).
6. Say hello to her. Type this in the Claude panel:
   ```prompt
   What can CLARA do?
   ```

:::check
CLARA greets you briefly and lists what she can do: draft prior-knowledge summaries, interview guides, research syntheses, personas, journeys, PRDs and test plans, and set up a Knowledge Base. In your IDE's file list you can see `.claude/skills/clara-gitlab/SKILL.md`.
:::

:::watch{title="If CLARA does not answer"}
Check three things. The folder is named `clara-gitlab`. The file inside is named exactly `SKILL.md`, in capitals. And the `.claude` folder sits at the top of the folder you have open in the IDE, not inside a subfolder. Folders that start with a dot may look hidden in Finder or File Explorer. In your IDE they still show in the file list.
:::

:::note{title="Installing at user level instead"}
To make CLARA available in every project, put the same three folders (`.claude`, `skills`, `clara-gitlab`) in your home folder instead of your workspace, with `SKILL.md` inside. Dot folders are hidden there by default. On a Mac, open your home folder in Finder and press :kbd[Cmd] + :kbd[Shift] + :kbd[.] to show them. On Windows, open File Explorer, go to your user folder and choose **View > Show > Hidden items**. If `.claude` already exists, add the new folders inside it.
:::
::::

::::tab{value="url" label="URL method"}
Nothing to download or install. You give Claude a starter prompt that tells it to read CLARA from a web address and follow it for the rest of the chat. Do this at the start of any chat where you want CLARA. It needs your computer to reach the address. If it cannot, use the file method.

1. Copy the starter prompt:
   ```prompt
   Read https://dsta-productops.github.io/clara/skill/clara-gitlab.md?v=3 and follow it as your instructions for the rest of this chat. Then introduce yourself and ask what I'd like to create.
   ```
2. Open a new chat in the Claude panel in your IDE and paste the prompt.

:::check
CLARA introduces herself and asks what you would like to create. She is now following her instructions for the rest of this chat. Start a new chat later and she is gone, so paste the prompt again.
:::

:::watch{title="If CLARA does not introduce herself"}
Check that you pasted the whole prompt, including the web address. Open the address in your browser to see whether it loads. If it does not, ask the contact below, or use the file method.
:::
::::
:::::

:::note{title="CLARA fetches her prompts from the web"}
When you ask for a document type, such as a persona, CLARA loads that prompt from the DSTA ProductOps site. If it cannot be reached, she asks you to paste the prompt. You can copy every one from the [Prompts](/prompts) page.
:::

## 2. Set up the SKYPROTECT Knowledge Base
::step{id="knowledge-base" phase="Research" tool="AI assistant"}

To follow along, you need a project that already has research in it. SKYPROTECT is a made-up drone-defence programme, and a setup file describes everything that belongs in its GitLab wiki: interview notes, personas, a journey map, a requirements document and a test plan. You hand that file to an AI assistant, and it builds the whole thing for you.

The assistant writes Markdown files into a local clone of the wiki, commits them and pushes. So it needs a shell with git. It uses plain git commands and nothing else. Run it from the Claude Code plugin in your IDE, with your workspace folder open. New to this? Do the optional setup step above first. If you did, list item 1 below is done and you can go straight to the download.

1. In GitLab, create an empty project called **SKYPROTECT** with its wiki enabled. Then initialise the wiki by creating a single first page titled `home` with any placeholder text, and copy the wiki clone URL (skip all of this if you did the optional setup step). Create the project and that first page yourself. The setup file tells the assistant not to create the project.
2. Download the setup file: :file[skyprotect-gitlab-setup.md]{href="/skyprotect-gitlab-setup.md"}.
3. In the Claude Code panel in your IDE, attach the file (or give it the path to the downloaded file) and paste this prompt. Replace the placeholder with your own wiki clone URL first:
   ```prompt
   Set up the SKYPROTECT demo Knowledge Base in a GitLab wiki by following the attached setup file exactly. The wiki clone URL is <paste your wiki clone URL>. The project and its wiki already exist, so do not create them. Use plain git commands only, with the git credentials already on this machine. If anything cannot be written, committed or pushed, stop and tell me. Do not retry or improvise.
   ```
4. Wait for it to finish. It writes the files in order, runs a link check, makes three commits and pushes once. When it is done, it reports how many files it created and gives you the link to the wiki home page.
5. Open that link in GitLab. It looks like `https://<your-gitlab-host>/<group>/skyprotect/-/wikis/home`. Look around.

::screenshot{hint="the SKYPROTECT wiki home page in GitLab, with the sidebar tree expanded"}

:::check
The wiki sidebar shows **Knowledge Base** with two tracks, **Programme-wide** and **Operator-console**. Each holds its own groups of pages: prior knowledge, field notes, research synthesis, personas, journeys, PRDs and test plans. In all, the assistant creates 52 pages, including 24 interview and observation notes (S01 to S16, WT01 to WT04, and the Field Alpha and Bravo shift notes). Click any citation in the research synthesis, such as S08, and it opens that note.
:::

:::watch{title="If the assistant stops part-way"}
That is by design. It stops and tells you what went wrong instead of guessing. Common causes are a wiki that was never initialised, no push access (you need the Developer role or above), missing git credentials, or a wrong clone URL. Fix that, then start again with the same prompt. Pages that already exist with identical content are skipped. The one exception is your placeholder `home` page, which it replaces. If any other page exists with different content, it stops and does not overwrite it.
:::

:::note{title="Page titles look like file names?"}
Page titles come from a front-matter block at the top of each file. Older GitLab versions ignore it and title pages from the file name instead. Everything still works. Titles are just plainer.
:::

:::note{title="The demo already has finished examples"}
The setup also files a finished example of most documents you make in steps 3 to 10. Each step tells you where to find it. Open it first to see what good looks like, then run the prompt and compare your result with it.
:::

:::note{title="Using your own project later?"}
SKYPROTECT is demo data. For a real programme, tell CLARA to create the folder structure instead. See [the CLARA provisioning steps](/tools/clara#provisioning).

## 3. Find what is already known
::step{id="prior-knowledge" phase="Research" tool="CLARA"}

Someone has probably worked on a similar problem before. Past projects, earlier write-ups and other teams' wiki pages are the first place to look for anything related to SKYPROTECT. This step stops you starting from zero.

1. Paste this prompt into CLARA:
   ```prompt
   Use CLARA's `prior-knowledge-summariser` for SKYPROTECT.
   ```
2. Answer her questions: your programme name, your track (or Programme-wide), and the topic. Be specific. "How operators hand over between shifts" works better than "user research".
3. Give CLARA your sources as **URL links** to wiki pages, one link per page. She looks for candidates in your local wiki clone, shows you the list, then reads the pages.
   ```
   https://<your-gitlab-host>/<group>/<project>/-/wikis/<page-path>
   ```
4. Check the list of sources she plans to use *before* she writes the summary. Remove pages that do not belong.

::screenshot{hint="CLARA's list of sources, with the page links she has picked up"}

:::note{title="CLARA asks before she writes"}
Before anything is filed, CLARA shows you the draft, the exact path, and every file that will change: the page itself, its entry in the folder's index page, and the sidebar. She files only when you say go. Each filing is one commit, pushed to the wiki.
:::

:::check
A summary of what past projects learned: patterns, contradictions and related work. Every finding names the wiki page it came from. It is filed under `[track]/Prior-knowledge/[topic]`.
:::

:::note{title="A finished example to compare with"}
Open `Programme-wide/Prior-knowledge/Counter-drone-systems` in the SKYPROTECT wiki.
:::

:::watch{title="Treat a missing source as a warning"}
A finding with no source is a guess, not a fact. A wrong page picked up here carries through every step that follows, so it is worth a minute to check now. If the summary feels thin, make your topic narrower and run it again.
:::

## 4. Measure how things are today
::step{id="baseline" phase="Research" tool="DASH"}

A **baseline** is a measurement of how things work today. Without one, you cannot show later that your new design is better. Do this before any interviews or design work.

DASH does two jobs. It runs surveys, which you use now and again when you test your prototype. It also tracks **OKRs** (objectives and key results): goals with numbers attached.

1. Sign in at [diux-dash.com](https://diux-dash.com) and open your programme's workspace.
2. Create a new session. Choose **Baseline Testing** and name the system people use today. For SKYPROTECT, that is the current three-vendor toolchain: separate radar, RF and camera systems.
3. Review the questions DASH generates. They cover:
   - **SUS** (System Usability Scale): a short questionnaire that scores how easy a system is to use.
   - Look and feel.
   - What users need from the system.
   - System performance.
   - **CSAT** (customer satisfaction): how happy people are overall.
4. Share the link or QR code that DASH gives you with people who use the current system.

::screenshot{hint="the Baseline Testing session in DASH, showing the share link and QR code"}

:::check
Responses appear in DASH as people answer. Keep this session open. You compare against it in step 11.
:::

## 5. Interview your users
::step{id="interviews" phase="Research" tool="CLARA"}

Surveys give you numbers. Interviews tell you why. CLARA writes the interview guide, and you run the conversations.

1. Paste this prompt into CLARA:
   ```prompt
   Use CLARA's `interview-guide-generator` for SKYPROTECT.
   ```
2. Tell her the topic and what you want to learn. If you are not sure, ask her to choose from the open questions in your prior-knowledge summary.
3. Run 5 to 7 conversations with the people who will use the system. **For SKYPROTECT, skip this.** The 24 interview, walk-through and field notes are already filed under `Field-notes` in both tracks.
4. For your own project, save your notes as a new page after each conversation. In the wiki, copy `Template-Field-note` in the track's `Field-notes` folder, give your copy a hyphenated name, and fill it in. CLARA gives it a short label such as S17 the next time she runs.

:::watch{title="Do not tidy your notes"}
Paste them exactly as you took them. Polished notes add your own bias, and CLARA does the interpreting in the next step.
:::

:::check
A field-ready interview guide with questions, things to listen for and follow-up prompts. Your raw notes sit in the `Field-notes` folder of the Knowledge Base.
:::

## 6. Make sense of the notes
::step{id="synthesise" phase="Research" tool="CLARA"}

1. Paste this prompt into CLARA:
   ```prompt
   Use CLARA's `research-synthesiser` for SKYPROTECT.
   ```
2. Give her your learning goals and the gaps you found in step 3. She uses them to judge what counts as new.

:::note{title="A finished example to compare with"}
Open `Operator-console/Research-synthesis`. The programme-wide version is under `Programme-wide/Research-synthesis`.
:::

:::check
One research-synthesis page with recurring patterns, friction points, standout statements and success criteria (what a win looks like). It cites your field notes, and the Knowledge Base is updated.
:::

## 7. Profile your users
::step{id="personas-journeys" phase="Research" tool="CLARA"}

Now CLARA turns the research into three documents. Run each prompt in turn. You do not need to learn the formats first.

### Persona

A **persona** is a profile of a typical user: what they want, what frustrates them, and evidence from your notes.

```prompt
Use CLARA's `persona-generator` for SKYPROTECT.
```

### User journey

A **user journey** maps the steps a person goes through, the moments that matter most, and where you could improve things.

```prompt
Use CLARA's `journey-map-drafter` for SKYPROTECT.
```

### Service blueprint

A **service blueprint** adds a layer to the journey. It shows what the user sees, what your team does behind the scenes, and the systems that support both.

```prompt
Use CLARA's `service-blueprint-drafter` for SKYPROTECT.
```

:::note{title="Finished examples to compare with"}
The space has a persona at `Operator-console/Personas/Console-operator` and a journey at `Operator-console/Journeys/Engage-incoming-threat`. It has no service blueprint, so yours is the first.

Three new pages in the Knowledge Base, each with an entry in its folder's index page and in the sidebar. Each claim points back to a quote or note from your research.

## 8. Write the requirements
::step{id="prd" phase="Research" tool="CLARA"}

A **PRD** (product requirements document) is one page that everyone agrees on: the problem, who it is for, what the product must do, and how you will know it worked. It is the most important output of the Research phase.

1. Paste this prompt into CLARA:
   ```prompt
   Use CLARA's `prd-generator` for SKYPROTECT.
   ```
2. Read what she drafts, then edit it by hand. The PRD becomes the input for your prototype.

:::note{title="A finished example to compare with"}
Open `Operator-console/PRDs/Console-v1`.
:::

:::check
A PRD with a problem statement, user goals, scope, functional requirements (what the product must do) and user stories (short descriptions of what a user wants to do and why).
:::

## 9. Build a prototype
::step{id="prototype" phase="Design" tool="Claude Code + PRIZM"}

A prototype is a working draft that people can click through. You will build it with Claude Code, which reads your PRD and PRIZM's rules, so the result follows DSTA standards without extra styling work.

1. Install Claude Code if you have not already. Follow the steps on the [Claude Code page](/tools/claude-code). As in the setup step, install the plugin in your IDE, not the command-line version or the desktop app. Open an empty project folder in the IDE and start a chat in the Claude panel.
2. Open the [Prototype-from-PRD scaffolder](/prompts/prototype-from-prd) prompt and paste in your PRD where it asks for it. The prompt tells Claude Code to read PRIZM's `PRIZM.md` and `llms.txt` first.
3. Choose a PRIZM zone. Pick **Enterprise** for websites and back-office tools. Pick **C3** for command-and-control systems.
4. Claude Code lists the three to five main user flows and asks which to build first. Pick one. Do not skip this question. It stops Claude Code generating hundreds of lines you do not need.
5. Open the prototype in your browser. To change something, describe the change to Claude Code in plain English.

::screenshot{hint="the running prototype in the browser, next to Claude Code"}

:::check
A running prototype for the flow you picked, built from PRIZM components and using semantic colour tokens (such as `bg-bg` and `text-fg`), not raw colours.
:::

:::watch
If Claude Code invents components that PRIZM does not have, stop it. Ask it to check `lib/components-registry.ts` in the PRIZM repository before it generates anything more.
:::

## 11. Test and compare
::step{id="test" phase="Test" tool="DASH"}

Now you close the loop. You test the prototype and compare the results with your baseline from step 4.

1. In DASH, create a new session and choose **Prototype Test**. It covers usability (SUS), look and feel, user needs and CSAT.
2. Share the link or QR code with your test participants, and run the sessions as set out in your test plan.
3. When the sessions are done, compare the results with your baseline session.
4. Ask **DASH AI** for recommendations. It suggests usability improvements based on industry standards.

::screenshot{hint="the DASH comparison view, baseline against prototype results"}

:::check

## If something goes wrong
::step{id="troubleshooting"}

CLARA builds on what you give her. If an early step is wrong, everything after it will be too, so it pays to check as you go.

### CLARA cannot see your wiki

Fix access first. Check that you can open the SKYPROTECT wiki yourself, that the wiki is enabled, and that you have the Developer role or above. Then ask the contact below to check CLARA's access to your wiki clone.

### The push is rejected, or authentication fails

CLARA and the setup assistant only use the git credentials already on your machine. Check that you can push to the wiki yourself. Never paste a token into a chat. If a push is rejected because the wiki changed, CLARA pulls, rechecks the path and retries once, then stops and tells you.

### An artefact landed in the wrong place, or cites nothing

Stop. Go back to steps 2 and 3. Check that the Knowledge Base exists and that your source links point to real pages with real content. Every citation should be a link to a note page.

### The output feels generic

CLARA says so when she has too little to go on. Add more source material, such as interview notes or past write-ups, and run the prompt again. A narrower topic also helps.

### You cannot find your DASH workspace

Each programme has one workspace. Ask the DASH contact to add you.
